## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-11.1-01 (Fix 1 — discovery skip, ~67-min win):** Skip FULL validation for a
  candidate sheet when its live Smartsheet `version` is unchanged vs
  `pipeline_memory.sheet_registry.last_sheet_version` AND a stored, non-empty
  `column_mapping` exists for it — reuse the stored mapping. Any other case
  (new sheet, version changed, registry row missing, registry/Supabase
  unreachable, version check itself fails) → FULL validation exactly as today.
  **Fail-closed is non-negotiable**: degraded mode is "validate everything"
  (today's behavior), never "skip validation". The INC-05 fail-closed guard from
  PR #373 (`_failed_validation_sids` → RuntimeError) must be preserved.
- **D-11.1-02 (Fix 2 — group-loop live confirmation, ~60-min win):** Keep the live
  existence-confirmation semantics of the PR #373 review fix (stub ≠ proof of
  existence) but remove the serial per-row `list_row_attachments` calls from the
  group loop. Replace with EITHER (planner picks with evidence): (a) one paginated
  sheet-level attachment listing per target sheet (`GET /sheets/{id}/attachments`,
  `include_all=True`), bucketed by `parentId` into the same memo
  `_live_row_attachments` reads, OR (b) a bounded parallel pre-fetch (≤8 workers,
  Smartsheet 300 req/min) of row listings for skip-candidate rows only, before the
  group loop. Transport failure → the affected rows resolve to "no live listing"
  → skip gate falls back to regeneration (same fail-open-to-regenerate posture as
  the current `_live_row_attachments` None-return).
- **D-11.1-03:** No re-introduction of local JSON caches, Actions cache steps, or
  the retired bulk attachment pre-fetch phases. Both fixes live inside the INC-05
  architecture (`sheet_registry` + `group_state` + live confirmation).
- **D-11.1-04:** Target: frequent-run wall clock back under ~75 min. Verified via
  the first post-merge run of THIS phase's PR (same measurement method as above).

## Summary

Both fixes are additive, surgical changes to two already-well-tested modules
(`pipeline/discovery.py`, `pipeline/orchestrate.py`). Neither fix requires a new
dependency, a schema change with any real risk, or touching the retired-cache
architecture. The single most important correction this research makes to
11.1-CONTEXT.md: **the installed and `requirements.txt`-pinned SDK is
`smartsheet-python-sdk==4.3.0`, not 4.0.0** — pinned since 2026-07-21 per the
pin comment ("4.0.1->4.3.0 changelog reviewed 2026-07-21, additive-only").
Every SDK claim below was verified by reading `4.3.0`'s installed source
directly (`site-packages/smartsheet/`), not 4.0.0.

**Fix 1 (discovery skip).** `Sheets.get_sheet_version(sheet_id)`
(`GET /sheets/{id}/version`) exists and is cheap, but the bulk answer to
CONTEXT.md's Open Question 1 is `Sheets.list_sheets(include=['sheetVersion'],
include_all=True)` — confirmed both in the installed SDK source and on
Smartsheet's live API docs — which returns `.version` for every accessible
sheet in **one** HTTP call, comfortably inside "≤2 API calls for 121
candidates." The single choke point for the skip is the top of
`_validate_single_sheet(sid)` in `pipeline/discovery.py:314`, before its
`get_sheet(include='columns')` call. `pipeline_memory.sheet_registry` already
stores `name` and `column_mapping` (schema confirmed), but the existing reader
helper `get_sheet_watermarks()` does **not** currently select `name` — its
`select()` list needs a one-token addition. Also load-bearing:
`pipeline.fetch.get_last_sheet_versions()` is **empty** at Phase 1 discovery
time (its own docstring says so, and the call-site order in `orchestrate.py`
confirms it) — Fix 1 cannot reuse it and needs its own live-version source.

**Fix 2 (attachment-confirmation batching).** `Attachments.list_all_attachments
(sheet_id, include_all=True)` (`GET /sheets/{sheetId}/attachments`) is
confirmed — both in the installed SDK source and Smartsheet's live API docs —
to return sheet-, row-, **and** discussion-level attachments with
`parent_type` (`SHEET`/`ROW`/`COMMENT`) and `parent_id` fields, so option (a)
from D-11.1-02 (one bulk listing per target sheet, bucketed by row) is
concretely viable — 2 API calls total instead of up to ~1,900+ serial ones.
The highest-value finding here: **`_live_row_attachments()` and both of its
two call sites do not need to change at all.** The function already has a
`if row_id in memo: return memo[row_id]` fast path reading the very
`_live_attachment_listings` dict this fix needs to pre-populate — so the
surgical implementation is "fill the dict before the loop," not "rewire the
call sites." That means `LiveRowAttachmentsTests` and
`SkipGateLiveConfirmationWiringTests` (both in `tests/test_incremental_read.py`)
need **zero** changes, contrary to CONTEXT.md's expectation that the
source-pin tests "WILL need updating."

**Primary recommendation:** Fix 1 — one `list_sheets(include=['sheetVersion'],
include_all=True)` call up front, threaded into `_validate_single_sheet` by
closure, registry watermarks fail-open exactly like every other
`pipeline_memory.reader` function. Fix 2 — option (a) (2 bulk
`list_all_attachments` calls, bucketed by `parent_id`), pre-seeding
`_live_attachment_listings` before the group loop, with a cheap `total_count`
pre-flight probe (the `IndexResult.total_count` field, confirmed to exist) to
size the response before committing, since TARGET_SHEET_ID's real attachment
volume cannot be measured from static source alone.

### Fix 1 — Discovery validation skip

**What:** Insert a registry-version fast path at the top of
`_validate_single_sheet(sid)` (`pipeline/discovery.py:314`), fed by data
gathered ONCE before the `ThreadPoolExecutor` block starts (`pipeline/
discovery.py:543-544`), not per-sheet inside the loop.

**Why this exact spot is the choke point [VERIFIED: pipeline/discovery.py:188-572].**
`base_sheet_ids` (the ~121-candidate list: 76 hardcoded ids plus
folder-discovered ones) is fully finalized by line 310, well before the
executor loop begins:

```python
with ThreadPoolExecutor(max_workers=PARALLEL_WORKERS_DISCOVERY) as executor:
    futures = {executor.submit(_validate_single_sheet, sid): sid for sid in base_sheet_ids}
```
`[VERIFIED: pipeline/discovery.py:543-544]`

`_validate_single_sheet` is a nested closure (already closing over `client`,
`sid`); it currently opens with:

```python
sheet = smartsheet_call_with_retry(
    client.Sheets.get_sheet, sid, include='columns',
    label=f"validate sheet {sid}",
)
```
`[VERIFIED: pipeline/discovery.py:322-325]`

and returns, on success:

```python
return {'id': sid,'name': sheet.name,'column_mapping': mapping}
```
`[VERIFIED: pipeline/discovery.py:510]`

Since the registry-hit fast path returns the *identical* 3-key shape from
already-fetched data, the Phase-09-frozen return contract
(`{'id','name','column_mapping'}`, `[VERIFIED: pipeline_memory/writer.py:346]`)
is preserved exactly — no downstream consumer needs to change.

**Fail-closed guard interaction [VERIFIED: pipeline/discovery.py:526-529,540,555-571].**
`_failed_validation_sids` is appended to ONLY inside the `except Exception`
branch of the existing full-validation path:

```python
logging.warning(f"⚡ Failed to validate sheet {sid}: {e}")
sentry_capture_sheet_drop(sid, e)
_failed_validation_sids.append(sid)
return None
```
`[VERIFIED: pipeline/discovery.py:526-529]`

and the post-loop guard raises `RuntimeError` if that list is non-empty
`[VERIFIED: pipeline/discovery.py:555-571]`. **The registry-skip fast path,
and any failure of the version probe or registry read that feeds it, must
never append to this list** — a version-probe failure means "cannot confirm
the skip is safe," which per D-11.1-01 must fall through to the *existing*
full-validation branch (which already has its own, separate, unchanged
failure handling). This is the concrete mechanism for "any doubt → full
validation": the skip check is a pure, side-effect-free short-circuit that
either returns a cached dict or does nothing (falls through), never raises
and never touches `_failed_validation_sids` itself.

**Where the two inputs come from:**

1. **Registry watermarks.** `pipeline_memory.sheet_registry` schema
   `[VERIFIED: pipeline_memory/schema.sql:68-80]`:
   ```sql
   CREATE TABLE IF NOT EXISTS pipeline_memory.sheet_registry (
       sheet_id            BIGINT      PRIMARY KEY,
       name                TEXT        NOT NULL,
       kind                TEXT        NOT NULL
           CHECK (kind IN ('primary', 'subcontractor', 'original_contract')),
       folder_id           BIGINT,
       column_mapping      JSONB       NOT NULL,
       last_sheet_version  BIGINT,
       last_read_at        TIMESTAMPTZ,

   ```
   `name` and `column_mapping` are both there, `NOT NULL`. But the existing
   reader helper's `select()` list omits `name`:
   ```python
   .select(
       "sheet_id,last_sheet_version,last_read_at,"
       "last_full_read_at,column_mapping"
   )
   ```
   `[VERIFIED: pipeline_memory/reader.py:115-118]` — **this needs `,name`
   added.** `get_sheet_watermarks()`'s fail-open contract (empty dict on any
   client/transport/response failure, documented at
   `[VERIFIED: pipeline_memory/reader.py:1-9,97-102]`: *"A read failure here
   means 'cannot confirm' — the caller ... MUST fall back to a FULL read"*)
   already gives Fix 1 exactly the fail-closed semantics D-11.1-01 requires,
   with zero new failure-handling code needed on the discovery side — a
   missing dict entry for `sid` (whether from a transport failure or a
   genuinely-new sheet) is indistinguishable and both correctly fall through.
   `SheetWatermarksReadTests` (`tests/test_incremental_read.py:207`) already
   covers this function and will need a matching update once `name` is added
   to the select list.

2. **Live sheet version.** `pipeline.fetch.get_last_sheet_versions()` looks
   like the obvious source but is **not usable** — its own docstring says so:
   ```python

       """Return a defensive copy of the per-sheet ``Sheet.version`` watermark
       captured during the most recent ``get_all_source_rows()`` call.

       Empty before the first call this run (the sheet_registry hook's first

       ``pipeline/orchestrate.py``'s two-pass registry-write comment).
       """
   ```
   `[VERIFIED: pipeline/fetch.py:90-97]`. Phase 2 (the fetch that populates
   this dict) runs strictly *after* Phase 1 discovery
   `[VERIFIED: pipeline/orchestrate.py:2163-2178]` — so at the moment
   `_validate_single_sheet` needs a live version, this dict is empty by
   construction. Fix 1 needs its own live probe, answered below by the SDK
   investigation.

**SDK Question 1 — cheapest live-version source [VERIFIED against installed
smartsheet-python-sdk 4.3.0 source, cross-checked against Smartsheet's live
API docs]:**

| Call | Cost for 121 candidates | Notes |
|------|--------------------------|-------|
| `Sheets.get_sheet_version(sheet_id)` — `GET /sheets/{id}/version` | 121 calls (1 per candidate) | `[VERIFIED: site-packages/smartsheet/sheets.py:644-661]`. Returns a `Version` object with only `.version` `[VERIFIED: site-packages/smartsheet/models/version.py:24-48]`. Official docs confirm: *"a number that represents the current sheet version"*, no special rate-limit weighting noted `[CITED: developers.smartsheet.com/api/smartsheet/openapi/sheets/get-sheetversion]`. |
| `Sheets.list_sheets(include=['sheetVersion'], include_all=True)` — `GET /sheets` | **1 call** | `[VERIFIED: site-packages/smartsheet/sheets.py:683-723]`. Docstring: *"include (list[str])... Valid list values: ownerInfo, sheetVersion, source"*, *"include_all (bool): If true, include all results (i.e. do not paginate)."* Official docs confirm `sheetVersion` adds `.version` to every returned sheet and explicitly note it *"should not be combined with pagination"* — i.e. pair it with `include_all=True`, not manual `page`/`page_size` `[CITED: developers.smartsheet.com/api/smartsheet/openapi/sheets/list-sheets]`. |

**This answers CONTEXT.md Open Question 1 directly: `list_sheets(include=
['sheetVersion'], include_all=True)` is the ≤2-call bulk variant.** It
returns every sheet the API token can access (a superset of the 121
candidates — filter to `base_sheet_ids` client-side, discard the rest). The
transport layer issues one HTTP request per `request()` call with no
client-side pagination loop `[VERIFIED: site-packages/smartsheet/
smartsheet.py:278-306]` — `includeAll=true` is a server-side directive, so
this genuinely is one round trip, not one-call-per-page. Recommended: wrap
this call in the existing `smartsheet_call_with_retry` (already imported in
`discovery.py`, same resilience pattern as the `get_sheet` call it's
replacing for skip-eligible sheets). Any exception from this call (retries
exhausted) must be caught locally and treated as "no live version data this
run" — every candidate then falls through to full validation; this is NOT
a `_failed_validation_sids` case.

**Fallback if `list_sheets` misses a candidate.** A candidate sid absent from
the bulk `list_sheets` response (edge case — e.g. a sharing/permission
anomaly) simply has no entry in the `{sheet_id: version}` dict built from it,
which the skip check already treats as "no live version available for this
sid" → falls through to full validation. No special-case code needed; the
"any doubt → full validation" rule is satisfied by dict-miss semantics alone,
the same pattern `get_sheet_watermarks` already uses.

### Fix 2 — Attachment-confirmation batching

**What:** Pre-populate `_live_attachment_listings` (currently `{}` at
`pipeline/orchestrate.py:2776`) before the group loop begins, using bulk
sheet-level attachment listings. **Do not modify `_live_row_attachments` or
either of its two call sites.**

**Why "don't touch the call sites" is the surgical answer.**
`_live_row_attachments` already memoizes by `row_id`:

```python
def _live_row_attachments(
    client: Any, sheet_id: Any, row_id: Any, memo: dict | None,
) -> 'list | None':
    ...
    if memo is not None and row_id in memo:
        return memo[row_id]
    try:
        listing = client.Attachments.list_row_attachments(
            sheet_id, row_id
        ).data
    except Exception:
        return None
    if memo is not None:
        memo[row_id] = listing
    return listing
```
`[VERIFIED: pipeline/orchestrate.py:1175-1205]`

The two skip-gate call sites both already pass the SAME module-level
`_live_attachment_listings` dict as `memo`:

```python
has_attachment = _has_existing_week_attachment(
    client, TARGET_SHEET_ID, target_row,
    str(wr_num), week_raw, variant, file_identifier,
    cached_attachments=_live_row_attachments(
        client, TARGET_SHEET_ID, target_row.id, _live_attachment_listings,
    ),
)
```

### Anti-Patterns to Avoid

- **Rewiring `_live_row_attachments` or its call sites for Fix 2.** Unnecessary
  churn against 3 pinned test classes when pre-seeding the existing memo dict
  achieves the identical performance result with zero call-site changes.
- **Reusing `pipeline.fetch.get_last_sheet_versions()` for Fix 1.** It is
  empty at Phase 1 time by construction (Phase 2 populates it, and Phase 2
  runs after discovery) — this would silently make the skip permanently
  inactive on every run (always "no live version" → always full validation),
  which is fail-closed-safe but defeats the entire point of the fix without
  raising any error to reveal the mistake.
- **Treating a version-probe or watermark-read failure as sheet-validation
  failure.** Only the existing `except Exception` branch around the full
  `get_sheet(include='columns')` call may append to `_failed_validation_sids`.
  A registry/version-probe miss must silently fall through to that same
  existing full-validation branch, never raise on its own.
- **Building a NEW two-phase, time-budgeted attachment pre-fetch.** D-11.1-03
  explicitly forbids reintroducing the retired pre-fetch architecture. Option
  (b), if chosen, must be a single bounded pass scoped to skip-candidates,
  with no new `*_MAX_MINUTES` / `*_TIMEOUT_SEC` constants.

## Common Pitfalls

### Pitfall 1: Assuming skip-candidate rows are known before the group loop runs
**What goes wrong:** Option (b) for Fix 2 needs to prefetch listings for only
the rows that are actual skip-candidates (unchanged-hash groups), but that
determination (`_hash_unchanged`, `_history_eligible_for_skip`) currently
happens *inside* the per-group loop body, not in a separate pass.
**Why it happens:** The group loop interleaves hash comparison, skip
decision, and Excel generation in one pass; there is no existing
"pre-compute which WRs will be skip-candidates" step to hook into.
**How to avoid:** If option (b) is chosen, the plan must design a genuinely
new preliminary pass (likely reusing `pipeline_memory.reader.
get_group_state_content_hashes_by_wr` `[VERIFIED: pipeline_memory/
reader.py:504-594]`, already used by the change-detection path, bulk-fetched
once per WR set) to derive the candidate row set — this is real, new
complexity option (a) avoids entirely.
**Warning signs:** A plan that describes option (b) as a drop-in replacement
without describing this preliminary pass is underspecified.

### Pitfall 2: Bulk `list_all_attachments` response size is unmeasured
**What goes wrong:** Committing to option (a) without first checking
`total_count` on TARGET_SHEET_ID / SUBCONTRACTOR_PPP_SHEET_ID risks a single
very large HTTP response replacing many small ones — this could shift, not
eliminate, the cost.
**Why it happens:** Static source reading cannot reveal live data volume;
only a live API call can.
**How to avoid:** Schedule a cheap `page_size=1` pre-flight probe (reads only
`IndexResult.total_count`) as an explicit verification step before or during
implementation — see Validation Architecture.
**Warning signs:** A plan or PR that ships option (a) with no logged
attachment count from a real run.

### Pitfall 3: Treating "no live version data" as a validation failure
**What goes wrong:** If the new bulk version-probe call's exception handling
is written carelessly (e.g. a bare `except: _failed_validation_sids.append
(sid)` reused from the existing pattern), a transient Smartsheet API blip
during the ONE version-probe call would abort the entire run — exactly the
outcome D-11.1-01 says must never happen for a version-check failure (only
degrade to full validation).
**Why it happens:** Copy-pasting the existing per-sheet exception-handling
pattern without noticing it serves a different failure class (persistent
per-sheet failure vs. one-time bulk-probe failure).
**How to avoid:** Keep the version-probe's own exception handling completely
separate from `_validate_single_sheet`'s existing `except Exception` block;
a probe failure produces an empty/partial `{sheet_id: version}` dict, handled
by the same "dict miss → fall through" mechanism as a genuinely-new sheet.
**Warning signs:** Any code path where a Fix 1 network failure raises instead
of silently degrading to today's behavior.

### Pitfall 4: `EnumeratedValue` comparison for `parent_type`
**What goes wrong:** `Attachment.parent_type` is wrapped in the SDK's
`EnumeratedValue(AttachmentParentType)` type `[VERIFIED: site-packages/
smartsheet/models/attachment.py:37-46]`, not a bare Python `Enum` member —
comparing it against `AttachmentParentType.ROW` vs. the string `'ROW'` vs.
`.value` may not behave as naively expected depending on `EnumeratedValue`'s
`__eq__` implementation (not read in this session).
**Why it happens:** SDK wrapper types frequently implement custom equality;
assuming standard Python enum comparison semantics without testing is a
common integration bug.
**How to avoid:** Write a unit test against a real (or realistically mocked)
`Attachment` object confirming the exact comparison form that correctly
identifies `ROW`-type attachments before relying on it in the bucketing
logic. Flagged as `[ASSUMED]` below — this is the one piece of Fix 2's design
this research could not fully pin down from source alone.
**Warning signs:** A bucketing function that silently produces an empty dict
because the equality check never matches.
