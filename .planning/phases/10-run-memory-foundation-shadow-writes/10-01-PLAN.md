`pipeline_memory/` package with its own Supabase client, a fail-open writer, an

<assumption_delta_decision>
Fired by the Assumption-Delta detector (kind: pluralization). The generalization
this phase introduces is that ONE generated file no longer has ONE target sheet:
a `reduced_sub` / `reduced_sub_helper` group fans out into TWO upload tasks —
one to `TARGET_SHEET_ID` and one to `SUBCONTRACTOR_PPP_SHEET_ID`
(`pipeline/upload.py` lines 300-347) — each producing its own Smartsheet
attachment with its own id.

- **Primary noun (generalized):** the *(group, target sheet)* pair — one persisted
  memory row per file actually attached to a specific sheet.
- **Decision:** `promote`. `group_state`'s primary key becomes
  `(wr, week_ending, variant, identifier, target_sheet_id)`, a strict superset of
  the design-spec draft's `(wr, week_ending, variant, identifier)`.
- **Rationale:** the draft key can hold only one `attachment_id` per group, so a
  two-leg fan-out would silently overwrite one leg's attachment id with the
  other's — the fan-out leg would be storable but never confirmable. Adding a
  second nullable `ppp_attachment_id` column alongside the old key (the
  add-alongside option) would encode the current two-sheet special case into the
  schema and break again at a third sheet. Promoting the target sheet into the key
  is the generalization the code already has.
- **Invariant test suggested (accepted, implemented in plan 10-03):** every upload
  task that reports success has exactly one `group_state` row keyed by its own
  `target_sheet_id`, for every variant including both legs of a `reduced_sub`
  fan-out.
</assumption_delta_decision>
