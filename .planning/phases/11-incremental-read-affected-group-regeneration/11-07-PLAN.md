<objective>
Land D-09's parity streak scan and the blocking-human decision gate that authorises the
INC-05 retirement. This plan produces the evidence and takes the decision; plan 11-08
performs the removals.

Purpose: the INC-05 retirement removes the live rollback path — three local JSON caches
and two attachment pre-fetch phases — and D-12 rates its undo cost as costly. What
authorises it is a run of five consecutive `pass` parity verdicts on `production_frequent`
runs. That evidence must be derived from `run_ledger` on demand and be auditable, because
a falsely satisfied streak is what turns a costly change into a bad one.

Output: `get_parity_streak` in `pipeline_memory/reader.py` with pass-counts /
fail-resets / skipped-excluded semantics, its `ParityStreakTests` regression class, and
the recorded decision from the blocking checkpoint.

**The retirement itself is plan 11-08** — cut as its own PR, strictly after this plan's
streak reading, and never bundled (D-12). Splitting the evidence-and-decision from the
removals keeps the highest-risk edits (a protected workflow file and two costly-to-revert
code removals) out of the same execution context as the query that authorises them.
</objective>

  <behavior>
    - Scanning newest-first over `run_ledger` rows whose `notes.execution_type` is `production_frequent`: five consecutive `pass` verdicts returns a streak of five.
    - A `fail` encountered before five passes resets the count to zero and stops the scan.
    - A `skipped` verdict is excluded from the sequence entirely: it neither increments the count nor resets it, and the scan continues past it.
    - A row with no `parity_verdict` in `notes` is treated the same as `skipped` — excluded, never counted.
    - Rows whose `notes.execution_type` is not `production_frequent` are ignored by the scan.
    - A Supabase failure returns None, which the caller reads as "cannot confirm" — never as a satisfied streak.
    - The scan reads a bounded window of recent rows rather than the whole table, and reports how many rows it examined so a streak of five is auditable.
  </behavior>
  <action>
    Implement CONTEXT.md D-09. Add `get_parity_streak(limit)` to `pipeline_memory/reader.py`: select `run_id`, `started_at`, `status`, `notes` from schema `pipeline_memory`, table `run_ledger`, ordered by `started_at` descending, limited to a bounded recent window. Give it `op="run_ledger_parity_streak"`.

    Walk the returned rows newest-first. Skip any row whose `notes.execution_type` is not `production_frequent`. For the remaining rows read `notes.parity_verdict`: a `pass` increments the count, a `fail` resets the count to zero and stops the scan, and both a `skipped` verdict and an absent verdict are excluded — the scan moves on without touching the count. Stop once the count reaches the target.

    Return a small dict carrying the streak count, the number of rows examined, the run ids that contributed, and the run id and verdict that stopped the scan if one did — so a claim of five is auditable rather than a bare integer. Return None on any failure, and document that None means "cannot confirm", never "streak satisfied".

    Do not add a counter column to the schema and do not cache the count anywhere. The whole point of deriving it on demand is that it cannot drift from the evidence.

    Add a `ParityStreakTests` class to `tests/test_incremental_read.py` covering all seven behaviors, driving the reader with a mocked Supabase response holding a crafted sequence of verdicts. The load-bearing tests are: a `skipped` sandwiched between passes does not break a streak, and a `fail` resets it. Write the tests first and watch them fail.
