<objective>
Ship INC-04's evidence machinery: the shadow-incremental parity proof (CONTEXT.md D-07)
and the shadow delta reads that exercise the watermark and escalation logic end-to-end
before the flag flips (D-08).

Purpose: ROADMAP success criterion 2 requires the incremental output set to equal the
full-run output set for five consecutive scheduled runs, and states that any divergence is
a blocking defect, not a tolerance. Alternating odd and even runs cannot produce that
evidence — Phase 10's own 10-06 lesson is that two separately scheduled runs are never
byte-identical on live data. The only honest comparison is in-process, on the same fetched
snapshot, within one run.

Output: `pipeline/parity.py`, a sub-budgeted hook in `orchestrate.py`, the
`parity_verdict` / `parity_details` keys in `run_ledger.notes`, and the shadow env-var
documentation. `run_summary.json` is not touched.

This plan is the first one that needs a populated `pipeline_memory`, so it opens with the
write-flip gate (D-10).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Shadow block → session time budget | The shadow adds Smartsheet calls to a run already sized against `TIME_BUDGET_MINUTES=165` under a 180-minute runner ceiling. |
| Shadow verdict → human decision to flip the incremental flag | The verdict is the sole evidence gating a production behaviour change; a false pass would authorise it wrongly. |
| Shadow block → the run's own generate/upload/cleanup actions | The shadow runs inside the production process; it must be provably inert. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-23 | Repudiation | Vacuous parity pass | critical | mitigate | Task 2: `pass` requires `groups_compared` greater than zero and both sides fully populated; every other outcome is `skipped` with a reason. Pinned by a test. |
| T-11-24 | Denial of service | Shadow block consuming the session budget | high | mitigate | Task 3: pre-flight guard, phase sub-budget, per-call timeout, and per-iteration stop, all copied from the two existing sub-budget implementations; `PARALLEL_WORKERS` is not raised. |
| T-11-25 | Tampering | Shadow mutating watermarks | high | mitigate | Task 3: the shadow reads watermarks and never writes them; pinned by a test asserting byte-equal `sheet_registry` payloads with the shadow on and off. A shadow-advanced watermark would make the next real run skip changed rows. |
| T-11-26 | Tampering | Shadow altering run behaviour on a fail | critical | mitigate | Task 2: the comparator computes and compares only; pinned by a test asserting identical generate, upload and cleanup call sequences with the shadow enabled and disabled. |
| T-11-27 | Information disclosure | `parity_details` in `run_ledger.notes` | medium | mitigate | `parity_details` carries group keys, hashes, counts, sheet ids and row ids — the same identifier classes Phase 10 already stores. No cell content, no price values, no personal data. |

| T-11-29 | Denial of service | Extra Smartsheet calls against the 300 requests-per-minute limit | medium | mitigate | Task 3 reuses the existing retry wrapper and the `PARALLEL_WORKERS` cap of 8; the probe is one call per unchanged sheet. |
