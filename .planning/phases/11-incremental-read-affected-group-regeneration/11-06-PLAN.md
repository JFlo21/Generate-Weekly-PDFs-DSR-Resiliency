Ship INC-03: the weekly deep run becomes a full read plus reconciliation. It detects
deletions that the frequent path structurally cannot see, refreshes
`sheet_registry.column_mapping`, and repairs `group_state` for groups whose membership
changed.

and the Smartsheet documentation, recorded as a durable finding in the Living Ledger
(`[2026-08-26 00:25]`) and locked as CONTEXT.md D-03. Without a reconciliation pass, a row
deleted in Smartsheet stays alive in `row_state` forever and keeps a group in the affected
set that has no business being there. The deep run is the only place this can be fixed,
and the Monday cron identity is what makes it identifiable.

reconciliation phase in `orchestrate.py`, the two fixtures, and the live-verification item

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Smartsheet full-read result → deletion inference | Absence of a row in a read result is being used as evidence that the row was deleted. A failed, truncated or partial read looks identical to a mass deletion. |
| Deep run → `row_state.deleted_at` and `group_state` | The reconciliation writes to the store that Phase 11 now uses to decide regeneration scope; a wrong deletion narrows future scope. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-30 | Tampering / destructive data loss | Deletion inference from a zero-row or partial read | critical | mitigate | Task 1: a sheet whose full read returned zero rows is skipped with a warning and a Sentry breadcrumb; a sheet not successfully read in full is skipped entirely. Absence in a partial read is never evidence of deletion. Pinned by tests. |
| T-11-31 | Tampering | Wrongly marked deletions narrowing future regeneration scope | high | mitigate | Task 1: `deleted_at` is written only on the `weekly_comprehensive` execution type after a successful full read, and `mark_rows_deleted` is fail-open — a failure leaves rows unmarked for the next deep run to retry rather than half-marking a sheet. |
| T-11-32 | Tampering | `group_state` repair nulling stored attachment ids | high | mitigate | Task 1: the repair goes through the existing `upsert_group_state` whose COALESCE preserves attachment ids — the same behaviour the flip PR's IN-01 item proves on a real upload. |
| T-11-33 | Tampering | Silently adopting a drifted `column_mapping` on a frequent run | high | mitigate | Task 2: only the deep run refreshes the mapping; a frequent run escalates that sheet to a full read via D-02 trigger 2 and never adopts the new mapping. Misgrouping is a billing-integrity defect. |
| T-11-34 | Elevation of privilege | New `row_state` UPDATE from the writer | low | accept | Same `service_role` client and the existing schema-wide UPDATE grant from Phase 10; no new grant, no schema change, RLS and REVOKE posture unchanged. |
| T-11-35 | Information disclosure | Deletion logs and Sentry breadcrumbs | low | mitigate | Logs and breadcrumbs carry sheet ids, row ids and counts only — no cell content, no price values. |
</threat_model>
