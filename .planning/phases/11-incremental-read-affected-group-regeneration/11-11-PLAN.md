<objective>
Close G-11-37 **mechanism A (hash-domain gap)**: the D-04 candidate set is derived from
`row_state.content_hash` deltas, but `row_state` hashes only `HASH_FIELDS` (16 + 4 Helper #2
fields) while the group hash (`calculate_data_hash` via `_extended_row_fields`) also reads
Dept #, Scope #/ID, Customer Name, Job #, Work Order #, CU Description, Unit of Measure, Area and
the raw Quantity/Snapshot text. An edit to any of those regenerates the group with no
`row_state` change, so the pair never enters the affected set and the shadow reports
`actual_not_in_candidate` (live: run 40584456830, WR 91427660 week 110126; reproduced
deterministically in `.planning/debug/inc02-candidate-divergence-post-fix.md`).

**Design chosen (no DDL) and the trade-off.** Two sound options exist:
1. *DDL option* — add the eight raw columns to `row_state`, the RPC column lists and
   `HASH_FIELDS`. That is exactly the deferred **D-05 Option B raw-column schema extension**,
   needs a protected `schema.sql` migration + RPC re-apply, and must be kept in sync with
   `change_detection.py` by hand forever (the same drift class that caused this gap).
2. *Chosen: hash-only fingerprint* — the caller (`pipeline/orchestrate.py`, which already
   pre-parses `__mem_quantity` for the same package-boundary reason) stamps
   `__mem_group_fp` = a SHA-256 over the row's own `_extended_row_fields(...)` output; the
   writer folds it into `content_hash` through a new `HASH_ONLY_FIELDS` tuple and strips it
   from the sent payload. Zero DDL, zero RPC change, drift-proof by construction (it calls
   the group hash's own function). Cost: `row_state` cannot say WHICH of the new fields
   changed (`row_event.after_image` shows identical business columns for an fp-only change)
   and every live row re-keys exactly once on the first post-deploy run (a one-time
   `row_event` burst, the same shape and precedent as Phase 14's D-14-08 "include-now").
Option 2 is equally sound for candidate selection (only hash inequality matters) and is the
DDL-minimising choice the owner asked for, so it is implemented.

**Billing-impact statement (owner constraint).** The `row_state` re-key does NOT cause any
Excel regeneration or upload: the skip/regenerate gate compares `calculate_data_hash()`
against the durable group hash (`billing_audit.group_content_hash` / `group_state`) plus
attachment existence and never reads `row_state`; with `RUN_MEMORY_INCREMENTAL_ENABLED` OFF
the affected set feeds only the shadow parity and `run_ledger` counters. Verified here by
byte-identity gates on every generation module + a static gate on the skip site, and live by
plan 11-15's owner checkpoint (upload count of the burst run vs its predecessor).

Expected one-time side effects of the burst run (document, do not "fix"): `rows_changed` ≈
live row count; the group verdict passes trivially (candidate = all pairs); the D-08
read-side verdict FAILS once (every re-keyed row is absent from the delta read), resetting a
streak that is already 0. If the burst exceeds `RUN_MEMORY_WRITE_MAX_MINUTES`, the remaining
sheets re-key on the next run(s) with the same harmless effect.

Purpose: make the candidate a superset of the full run's actual set for every row-content
edit — the precondition for a genuine ≥5-run streak.
Output: `pipeline/memory_candidate.py`, the writer hash-only field, the orchestrate stamp,
regression fixtures.
</objective>
