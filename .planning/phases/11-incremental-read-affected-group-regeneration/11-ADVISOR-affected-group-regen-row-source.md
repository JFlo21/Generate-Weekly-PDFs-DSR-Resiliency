**Rationale (advisor):** The repo already resolves more of this area than the prompt implied.
`upsert_rows_bulk` (`schema.sql:280-477`) returns the affected `(wr, week_ending)` set as the UNION
of each changed row's new pair *and* its prior pair when `week_ending` moved — the moved-week case
is done server-side; `units_completed` is already in `HASH_FIELDS` (`writer.py:460-477`), so an
un-accepted row is a normal content-hash diff, not a special case. True row *deletion* is the one
open piece: delta reads cannot observe an absence, `row_state.deleted_at` is reserved but never
written (Phase 10 OPT-OUT, `COVERAGE.md:33`), and INC-03/D-07 lock deletion reconciliation to the
weekly deep run — no frequent-run option should attempt it. The hard part is (3)/(4): `row_state`
carries 16 hash-relevant business fields while `grouping.py`/`excel.py` read dozens more — raw
(`Job #`, `Scope #`, `Work Order #`, `Customer Name`, `Dept #`, `CU Description`, `Unit of Measure`)
and derived attribution/pricing fields (`__current_foreman`, `__resolved_price`, `__variant`,
`__effective_user`) that the schema comments deliberately forbid storing resolved. That makes
Option A the one to steer away from — the literal "row_state exclusively" reading of INC-02 risks
silently changing billing output for a group whose Smartsheet data did not change. Option C is the
safest sequencing: ship INC-02's affected-group selection without touching the locked MEM-01 schema
or duplicating the attribution/pricing path; Option B is the natural next slice once C is clean
against the parity gate — at which point `group_state.content_hash` (already confirmed identical to
`calculate_data_hash()` / `hash_history.json` at `orchestrate.py:670`, not a competing hash) can
become the sole skip gate per INC-05.
