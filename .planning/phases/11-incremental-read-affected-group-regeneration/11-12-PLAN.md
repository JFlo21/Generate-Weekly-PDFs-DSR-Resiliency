<objective>
Close G-11-37 **mechanism B (regeneration-debt gap)**. `row_state` advances during the memory
write, before any upload, and the affected set is "changed this run" only. A run that is
cancelled, times out, or fails an upload strands groups whose durable group hash was never
advanced; the next run's row diff no longer contains them, but the full run regenerates them
(live: cancelled 40751825583, then manual 40757294483 regenerated ~12 groups vs 4 affected
pairs). Plan 11-13 separately decides whether runs that follow an unfinished run count toward
the streak at all (owner decision); this plan makes the candidate itself correct either way,
which the real incremental path also needs (a graceful time-budget stop finishes `success`,
so D-02 trigger 6 never fires for it).

**Design (no DDL) and the trade-off.** A durable "dirty pair" column or table would need
protected DDL. The equally sound non-DDL carrier is `run_ledger.notes` (JSONB, already
written at start/finish, service-role UPDATE granted): each run records its pending candidate
pairs right after the memory write and, at finish, the subset it could not confirm. The next
run unions the chain back to the most recent `success` row. Cost: one extra bounded SELECT
and one extra upsert per run; pair lists are capped (`REGEN_DEBT_MAX_PAIRS = 5000`, beyond
which debt is UNKNOWN and resolves conservatively). The chain is self-healing in full mode
(every full run re-confirms everything), so UNKNOWN costs at most one `skipped` verdict.

Purpose: candidate ⊇ actual across run boundaries, not just within one run.
Output: debt reducer + reader + writer note + orchestrate hooks + fixtures.
</objective>
