<objective>
Close G-11-37 **minor mechanism C**: `upsert_rows_bulk` returns `(new wr, prior week)` for a row
whose week moved, never `(prior wr, prior week)`, so a Work Request # edit on a row misses the
OLD WR's group (not observed in the cited runs; diagnosed from the RPC body, schema.sql lines
547-553).

**Why this is the one DDL plan, and the trade-off (owner constraint).** A non-DDL alternative
exists: after the RPC, look up each changed row's previous `row_event` (its `wr` column is the
prior identity) with a client-side SELECT. It is NOT equally sound: it adds a per-run read
proportional to changed rows (the whole table on a re-key burst), depends on `row_event`
retention (24-month purge) and on every prior state having an event, and is not atomic with
the upsert. The RPC already holds the exact prior row in its `prior` CTE inside the same
statement, so one additive `UNION` branch is the smaller, atomic, zero-round-trip fix. It is a
protected change (`pipeline_memory/schema.sql`; 11-CONTEXT D-04 planned zero schema change —
the owner's G-11-37 planning constraint explicitly allows an additive DDL plan behind an
approval checkpoint), so it ships in its own plan, additive only, with a rollback, and is
applied only after Juan approves. Deferring C entirely is a legitimate owner choice (Task 2).

Purpose: the candidate includes the old WR's group when a row changes WR.
Output: additive RPC branch in schema.sql + standalone migration with rollback + contract test;
live apply only on approval.
</objective>
