<objective>
Prove the whole audit-memory path end-to-end on one check type before expanding it.

This plan wires a single vertical slice: an emitted `rate_sanity_mismatch` finding travels
from `audit_results` through key derivation, the `week_ending` join, the `AUDIT_MEMORY_ENABLED`
gate, the per-op circuit breaker, and a correctly shaped `pipeline_memory.upsert_audit_findings`
RPC call — with the reapply-safe DDL that call targets checked into `pipeline_memory/schema.sql`.

Purpose: `rate_sanity_mismatch` is the only check whose emitted dict already carries all of
D-01's declared identity fields (`work_request`, `cu`, `work_type`), so it exercises every layer
without also carrying D-CD-01's multi-week ambiguity or D-CD-02's literal-string coupling. If the
architecture is wrong, it is wrong after one commit instead of after five.

Output: `pipeline_memory/audit_findings.py`, the `AUDIT_MEMORY_ENABLED` flag and its live re-read,
the two new tables plus the RPC skeleton in `pipeline_memory/schema.sql`, the orchestrate hook,
and `tests/test_audit_findings.py` (the Wave 0 test scaffold every later plan in this phase extends).
</objective>

    The exact canonical hash input for `finding_key` — whether it carries a leading recipe version

  <context>
    D-01 already fixes the identity fields per check; what is being confirmed here is the literal
    string layout that gets hard-coded in Task 2, because that layout is the durable contract.
    A later change to it orphans every open finding silently: the old key is simply never seen
    again, so the finding never transitions to `fixed` and never surfaces as a problem. Confirming
    it once, before it exists in code, costs one question; discovering it after the flag is on
    costs a rehash-and-event-row migration of every open finding.
  </context>
  <options>
    <option id="versioned-recipe">
      <name>Version-token-first canonical string (recommended)</name>
      <pros>
        A future recipe change becomes an explicit, named migration (`v1` -> `v2`) instead of a
        silent orphaning; costs one extra segment in the hash input and nothing at runtime; makes
        the migration boundary greppable in both Python and the stored rows.
      </pros>
      <cons>
        One more constant to keep in sync between the module and the stored `recipe_version`
        column; the token is dead weight if the recipe never changes.
      </cons>
    </option>
    <option id="unversioned-recipe">
      <name>D-01's fields only, no version token</name>
      <pros>
        Exactly what D-01 specifies, nothing added; the shortest possible canonical string.
      </pros>
      <cons>
        A future recipe change has no marker distinguishing old keys from new ones, so a migration
        has to infer which rows are stale; the orphaning failure mode stays silent.
      </cons>
    </option>
  </options>
