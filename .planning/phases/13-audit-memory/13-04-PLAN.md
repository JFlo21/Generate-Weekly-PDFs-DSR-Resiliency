<objective>
Make the finding lifecycle real: the full D-08 transition table server-side, and the AUD-02
re-audited-group scoping that decides which findings are even eligible to close.

Purpose: closing a finding is the single most dangerous operation in this phase. A too-wide
re-audited set closes findings the run never actually re-checked; a too-narrow one leaves a
corrected problem open forever. The rule is deliberately conservative — a finding transitions to
`fixed` only when its own check ran this run AND its own `(wr, week_ending)` group was in the
audited row set AND the check did not reproduce it.

Output: the complete `upsert_audit_findings` plpgsql function, the per-check re-audited-pair
computation on the Python side, the orchestrate wiring that supplies it, and a lockstep
Python-to-SQL contract test.
</objective>

explicit `jsonb_to_recordset(...) AS q(...)` / `AS r(...)` column lists — `p_findings` columns

Implement exactly these transitions and nothing else:

- **new key** (in `p_findings`, absent from `pipeline_memory.audit_finding`): insert with
  `status='open'`, `first_seen_run = p_run_id`, `last_seen_run = p_run_id`, `fixed_run` NULL, and

  `audit_finding_event` row with `transition='opened'`.
- **existing key present in `p_findings`**, by current status:
  - `acknowledged` -> `resurfaced`, event `resurfaced`
  - `fixed` -> `open` with `fixed_run` set to NULL, event `reopened`
  - `suppressed` -> status unchanged, event `seen`
  - `open` or `resurfaced` -> status unchanged, event `seen`

  In every one of those four cases `last_seen_run = p_run_id`, `updated_at = NOW()`, and the
  mutable non-identity columns (`severity`, `evidence`) are refreshed from the payload. Identity
  columns and `first_seen_run` are never overwritten.
- **existing key absent from `p_findings`**, eligible only when its `status` is `open` or
  `resurfaced` AND its check ran this run AND its group was re-audited: set `status='fixed'`,
  `fixed_run = p_run_id`, `updated_at = NOW()`, event `fixed`. `last_seen_run` is NOT bumped — the
  finding was not seen.

  "Its check ran this run AND its group was re-audited" means: a row exists in
  `p_reaudited_pairs` whose `check_id` equals the finding's `check_id` AND whose `(wr,
  week_ending)` equals the finding's — with one explicit exception: when the stored finding's
  `week_ending IS NULL`, a matching `check_id` plus matching `wr` is sufficient regardless of the
  pair's week (this is the D-CD-01 pooled-week rule). Write this as a join, never as a
  `NOT EXISTS` over the whole table, so an empty `p_reaudited_pairs` array can match nothing and
  therefore close nothing.
- **everything else**: untouched. No status change, no `last_seen_run` bump, no event row. In
  particular a finding whose `check_id` does not appear anywhere in `p_reaudited_pairs` is
  untouched even if every other check re-audited its group.

`RETURNS TABLE (opened INT, seen INT, fixed INT, resurfaced INT, reopened INT)` with the real
counts; `RETURN QUERY` a single summary row. Order-independence is inherent to the set-based CTE
form — do not introduce a per-row loop or an `ORDER BY` that could make the result order-sensitive.

Add a comment block above the function recording: `finding_key` arrives pre-computed from Python

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Python client JSONB -> service-role plpgsql function | Two client-shaped arrays drive INSERT, UPDATE, and status transitions on billing-adjacent audit data |
| Audited row set -> the decision to close a finding | The re-audited pair set is the sole authority for which findings may transition to `fixed` |
| Environment -> executed-check set | `RATE_SANITY_AUDIT_ENABLED` silently changes which findings are eligible to close |
| Python payload keys -> SQL recordset column list | Two independently editable artifacts that must stay in lockstep |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-13-04-01 | Tampering | `upsert_audit_findings` RPC input | high | mitigate | Explicit typed `jsonb_to_recordset(...)` column lists for both parameters; no dynamic SQL, enforced by a grep gate for `EXECUTE` / `format(` / `quote_` over the whole schema file |
| T-13-04-02 | Elevation of Privilege | new plpgsql body | high | mitigate | `SET search_path = ''` retained and every object reference schema-qualified; enforced by the `search_path` count gate |
| T-13-04-03 | Tampering (data integrity) | premature `fixed` transition | high | mitigate | The `fixed` branch is a join against `p_reaudited_pairs`, so an empty array closes nothing; per-check scoping prevents a disabled check's findings from closing; `last_seen_run` is deliberately not bumped on close so the audit trail distinguishes seen from closed |
| T-13-04-04 | Tampering (data integrity) | Python-to-SQL key drift | high | mitigate | Bidirectional lockstep contract test over the RPC parameters, the recordset column lists, and both CHECK value sets |
| T-13-04-05 | Repudiation | which run performed which transition | medium | mitigate | Every transition writes an `audit_finding_event` row carrying `run_id`, `transition`, and `observed_at`; `first_seen_run` is never overwritten by an update |
