### Attribution methodology note (repeated-message findings)

Findings #1-2, #5, #6, #7, #8, #9-10 belong to normalized-message groups that
already had one or more occurrences in the baseline at *different* line
numbers within the *same* file (e.g. `audit_billing_changes.py` already had 3
other `"object" has no attribute "extend"` findings, 5 other `"append"`
findings, and 2 other `< ("int" and "object")` findings before this delta).
Because the multiset diff strips line numbers, it cannot mechanically say
*which* physical line is "the new one" among several identical-message
lines — it only proves the *count* increased by a known amount per message
(here, by exactly 1 for each of the three `audit_billing_changes.py`
patterns, and by exactly 2 for the `pipeline/orchestrate.py`
annotation-unchecked pattern). To resolve the ambiguity without guessing,
every candidate physical line matching each repeated message was individually
`git blame`d:

- For the three `audit_billing_changes.py` patterns, every OLD line (present
  since baseline) blames to `3fd0bae` (2025-08-31, the pre-Phase-09 monolith
  commit — "Clean up codebase and restore billing audit system"), and
  exactly **one** line per pattern blames to `647a688` (2026-08-12, the
  rate-sanity audit feature) — a clean, unambiguous 1-for-1 match against the
  computed +1 delta per pattern.
- For `pipeline/orchestrate.py`'s annotation-unchecked notes, 12 of the 14
  current candidate lines blame to `5005040f` (2026-06-27, the Phase 09
  merge itself — these are the baseline's 12 occurrences, just line-shifted
  by later edits) and exactly **2** blame to `de43b79` (2026-07-06,
  post-Phase-09) — again a clean, unambiguous match against the computed +2
  delta.

This means every row in the table above is attributed to the specific
physical line git blame identifies as genuinely new, not merely "a line
matching a new-looking message."

## Observations

- **Windows backslash paths are a cross-platform hazard for Gate 4's
  FAIL-branch `diff`.** `tests/golden/mypy_baseline.txt` was frozen on
  Windows and stores `\` path separators (e.g. `billing_audit\client.py`,
  `pipeline\orchestrate.py`). mypy on Linux/macOS emits `/`-separated paths.
  If Gate 4 ever runs on Linux CI, its FAIL-branch `diff "$BASELINE_TXT"
  "$CURRENT_OUT"` (scripts/check_mypy_delta.sh line 74) would report 100%
  spurious line differences purely from the separator character — every
  single baseline line would appear to differ from every current line even
  when the actual finding is identical. The pass/fail *count* comparison
  (`new_count -gt baseline_count`, the actual gate logic) is unaffected
  because it only counts lines; only the diagnostic `diff` output printed on
  FAIL would be misleading. Flagged for awareness — not fixed here, and not
  in this plan's scope (the plan's scope is Gate 6 pinning + delta
  attribution, not Gate 4 internals beyond what `09-07` already hardened).
- **The multiset-diff removal (`audit_billing_changes.py:305` baseline-only
  `Unsupported left operand type for + ("object")  [operator]`) is not a
  new-finding attribution concern** — a removal cannot represent a
  regression — but is reported here for completeness so the arithmetic
  (10 new - 1 removed = +9 net, matching the raw 56->65 line delta exactly)
  is independently checkable from this report alone.
- **None of the 10 new findings originate in Phase 09 or in this v1.2
  milestone's Phase 08/09 work.** All four blame commits (`3b2f7b0`,
  `a6e19db`, `647a688`, `de43b79`) post-date the Phase 09 merge commit
  `5005040f` (2026-06-27) and are quick tasks / a debug-session fix applied
  directly to `master` between 2026-07-06 and 2026-08-13 — none appear in
  `.planning/ROADMAP.md`, confirmed by grep (zero matches for the relevant
  quick-task IDs, PR numbers, or `snapshot_drift`/`snapshot-date drift`
  strings in that file).
- **The VERIFICATION.md working hypothesis is partially confirmed, partially
  corrected.** It named `pipeline/retry.py` and `pipeline/snapshot_drift.py`
  as likely candidates for the delta. `pipeline/snapshot_drift.py` IS
  implicated (finding #4). `pipeline/retry.py` contributes **zero** of the
  10 new findings — the actual drivers not named in the hypothesis are
  `billing_audit/snapshot_store.py` (findings #1-3), new code appended to
  the already-loosely-typed dicts inside `audit_billing_changes.py`
  (findings #5-8), and 2 additional untyped functions added to
  `pipeline/orchestrate.py` by the `WR 11951363` skip-gate-deadlock fix
  (findings #9-10).
- **7 of the 10 new findings (class C) are not new categories of defect** —
  they are new lines of code that reuse an already-accepted, already-baselined
  pattern in the same file: the `try: from postgrest import APIError ...
  except: _APIError = ()  # type: ignore[assignment]` defensive-import idiom
  already used identically in `billing_audit/client.py:34/38` and
  `billing_audit/writer.py:919` (findings #1-2); the identical
  `Library stubs not installed for "dateutil"` `[import-untyped]` finding
  already present for `pipeline/orchestrate.py:40` (finding #4, now also in
  `pipeline/snapshot_drift.py`, which imports the same untyped third-party
  module); and 3 findings (#5-8) where `audit_billing_changes.py`'s
  systemically loosely-typed `audit_results`/`summary` dicts (`dict[str,
  object]`-shaped, already responsible for 13 baseline findings in the same
  file) picked up one new key each (`rate_sanity_mismatches`,
  `total_rate_sanity_mismatches`) that inherits the exact same typing gap —
  the code did not get *less* type-safe, it got *bigger* using the existing,
  already-tolerated shape.
- **1 finding (class B, findings #9-10) is pure line-count noise** — a mypy
  `note:` about unchecked untyped-function bodies, emitted only because
  `--check-untyped-defs` is not enabled project-wide; it represents zero
  behavioral risk.
- **1 finding (class A, finding #3) is the only candidate for a real
  correctness improvement**, and it is already runtime-guarded: `key =
  (int(row.get("sheet_id")), int(row.get("row_id")))` at
  `billing_audit/snapshot_store.py:370` is immediately wrapped by `except
  (TypeError, ValueError): continue` (line 371-372) in the same function, so
  a `None` value from `.get()` cannot propagate past this line as an
  uncaught exception — the row is simply skipped. The type annotation gap is
  real (mypy is correct that `row.get(...)` can return `Any | None`, which
  `int()` does not accept), but the surrounding code already defends against
  the failure mode mypy is flagging. **Recommended one-line fix (not
  applied):** replace the bare `int(row.get(...))` calls with an explicit
  guard, e.g. `_sid, _rid = row.get("sheet_id"), row.get("row_id")` then
  `if _sid is None or _rid is None: continue` before the `int(...)` pair —
  this would satisfy mypy without changing behavior, since the existing
  `except` clause already treats that path as "skip this row."
